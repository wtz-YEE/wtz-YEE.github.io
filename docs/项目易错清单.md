## 0. 30 秒排障顺序（先做这个，别急着改代码）

```
1. 服务端活着吗
   https://<隧道地址>/health            → 期望 {"ok":true}
   本地：http://127.0.0.1:8701/health   → 期望 {"ok":true}
2. 8701 端口有进程在听吗
   Get-NetTCPConnection -State Listen -LocalPort 8701
3. 前端从哪拿云端地址
   GitHub 上的 cloud.txt 内容 = 当前隧道地址吗？
4. 浏览器控制台 Network 里那条失败请求的真实状态码是多少
   ← 90% 的答案在这一步，不要跳过
5. 服务端数据文件是不是合法 JSON
   python scripts\xxx.py 或 json.load 试一下
```

**最重要的一条：永远先拿到真实 HTTP 状态码再动手。** 浏览器会把 500、CORS 失败、
断网统一报成「请求失败 / Failed to fetch」，按报错文案猜原因会浪费大量时间。

## 1. 云端连不上（已解决 · 2026-10-04）

### 现象
- 页面显示「云端不可达 / 云端离线」，留言、登录、访客墙全部拿不到数据
- 但 `https://<隧道地址>/health` 用浏览器/命令行直接打**是通的**

### 先查什么
1. 隧道地址还活着吗：打 `/health`
2. GitHub 上 `cloud.txt` 的内容 = 当前隧道地址吗
3. 浏览器 **DevTools → Application → Service Workers**：有没有旧的 SW 还活着
4. **DevTools → Application → Cache Storage → `wtz-site-*`** 里有没有 `cloud.txt` 条目
5. `localStorage['gb_api_url']` 里存的地址是不是旧隧道

### 真因
`sw.js` 只在 `index.html` 注册，**而且没写 scope，所以拿到整站作用域**。
它的 fetch 处理器把「同源 + 非 HTML + GET」一律走缓存优先，
`cloud.txt` 也落进了这个分支。

关键点：`cloud.txt` 请求虽然带了 `?t=Date.now()` 防缓存参数，
但 **Cache API 的 `caches.match()` 按 URL 匹配时会忽略 query**，
所以每次都能命中那条旧缓存 → cpolar 换过子域后，浏览器永远读旧地址。

> cpolar 的子域是**会变的**（历史上出现过 `36c3116e` / `1e5cfe73` / `58e29a49`）。
> 地址一变，这个坑必然复发。

### 怎么修（已完成）
- `sw.js`：`cloud.txt` 不再交给缓存，直接
  `e.respondWith(fetch('https://wtz-YEE.github.io/cloud.txt?t='+Date.now(),{cache:'no-store'}))`
  ——同时绕开 SW 缓存和浏览器 HTTP 缓存（GitHub Pages 给 `cloud.txt` 设了 `max-age=600`）
- `sw.js`：缓存名升到 `wtz-site-v4`（换名字才会触发旧缓存清理与 SW 更新）
- `index.html`：加 `cloudProbe()` / `cloudRecover()`——探活 `/health`，失败就重取
  `cloud.txt`，**只在地址真的变了才重连**，并支持多主机备用切换
- `guestwall.html`：原来是唯一「存了地址就永不刷新」的页面，改为先探活再决定
- `机密终端.html`：`ABASE` 原来只在页面加载时读一次，改为可重读（`setBase` / `savedBase`）
- 旧的帮助文案里写死的失效域名 `36c3116e.r21.cpolar.top` 已换掉

### 怎么别再来一次
- **凡是"配置/地址发现"类的同源 GET，都不要进 Service Worker 缓存。** 宁可多一次网络请求。
- 改 `sw.js` 后必须**改缓存名**，否则旧缓存不清理。
- 换云端地址后，如果页面还显示旧状态：**Ctrl+F5 强刷一次**。
- 排查时先看 Cache Storage 有没有 `cloud.txt`，这是最快的判据。

## 2. 登录失败（已解决 · 2026-10-04）

### 现象
- 点登录，界面提示「**请求失败**」（不是「账号或密码错误」，也不是「操作太频繁」）
- 前端文案「请求失败」只出自 `gbLogin()` 的 `.catch()`，即**网络层失败**

### 先查什么
1. **直接打接口拿状态码**：
   ```
   POST https://<隧道地址>/login
   Content-Type: application/json
   {"username":"wtz","password":"..."}
   ```
2. 如果返回 **500** → 往下看「数据文件损坏」
3. 如果返回 **429** → 是限流，不是损坏（见第 4 条）
4. 如果是 CORS 报错 → 注意：**错误响应（500）默认不带 CORS 头**，
   所以 500 在浏览器里长得像 CORS/网络失败

### 真因
`_gb/users.json` 内容 = 一段合法 JSON + **尾部多出来的残留字节**：

```
"Extra data: line 1 column 1230 (char 1229)"
合法 JSON 到第 1229 字符结束，后面还挂着 "}}"
```

后果分两条路，都很坑：
- `/login` 里 `json.load()` 抛异常且**没有捕获** → 返回 **HTTP 500**
- `_load()` 捕获异常后 `return d`（默认值 `{}`）→ **静默把整个账号库当成空库**，
  同步时可能把账号"同步没"（比 500 更危险，因为它不报错）

500 响应不带 CORS 头 → 浏览器报网络层失败 → 前端只显示「请求失败」，
真因被完全掩盖。

### 怎么修（已完成）
- 先修数据：把 `users.json` 截断到第一个合法 JSON 文档，**保留 7 个账号**
  （`asdf`、`asdfasdf` 两个是管理员自己删号/封禁的，**没有回滚**）
- 根因治理（`_gb` 和 `_cloud` 两份都改，保持一致）：
  - `_save()` 改**原子写**：先写 `*.tmp<pid>`，再 `os.replace()`，统一 `indent=1`
  - `_load()` 解析失败时**先抢救**第一个合法 JSON 文档并回写，
    失败才退化为默认值（不再静默清空账号库）
  - 9 处裸写 `with open(USER_FILE,"w")+json.dump` 全部改用 `_save()`
  - `_load/_save` **上移到文件顶部**，因为启动期初始化写入要用到（否则 NameError）

### 怎么别再来一次
- **写数据文件一律走 `_save()`，不要自己 `open(...,"w")` + `json.dump`。**
- 新增仓库根目录的 `.py` / `.md` 工具脚本时注意：服务端 `_BASE` 是脚本所在目录，
  所以**不要把会 import 服务端模块的脚本放到 `_gb/` 下**——顶端一旦 `app.run()` 会起重复实例。
- 改了服务端后自检：
  ```
  python -m py_compile _gb\guestbook_server.py
  python -m py_compile _cloud\guestbook_server.py
  ```
- 任何"读 JSON 失败就返回默认值"的写法都要警惕：**它会把故障从"报错"变成"静默丢数据"**。

## 3. 服务端 500 的排查套路

### 现象
接口 500，浏览器里表现成各种样子（请求失败 / 加载失败 / 无反应）。

### 先查什么
1. 直接 curl / fetch 那个接口，拿到真实状态码和响应体
2. 打开**运行服务的那个控制台窗口**看 traceback（服务是 `pythonw` 起的，看不到就临时前台跑）：

```
python _gb\guestbook_server.py
```

> 注意：临时前台跑之前**先停掉 8701 上的旧进程**，否则端口占用，新进程起不来，
> 你会以为"改的代码没生效"，其实是旧进程还在服务。

3. 挨个检查这个接口会读哪些数据文件，手工 `json.load` 验证是否合法

### 常见真因
- 数据文件损坏（见第 2 条）
- `request.get_json()` 返回 `None`：前端没带 `Content-Type: application/json`
- 用户记录缺字段：直接 `u["pwd"]` 这种写法，字段缺失就 `KeyError`
- 并发/半截写在文件末尾留下残留字节

## 4. 限流：`429 操作过快`

### 事实（代码位置 `_gb\guestbook_server.py`）
- `_WRITE_PATHS` 里的所有写接口受 **1.5 秒/IP** 限流
  （`/login` 也在里面！还有 `/hit`、`/register`、`/guest_add`…）
- `_rate()` 对 `OPTIONS` **直接放行**，所以 CORS 预检不会被限流误伤
- 前端 `ferr()` 会把含 `429` 的报错统一改写成「操作太频繁，请稍候几秒再试」

### 怎么别被它误导
- **手工连测接口时必须间隔 ≥1.6 秒**，否则你以为接口坏了，其实是限流。
- 排查"登录失败"时，如果拿到 429，先等 2 秒再试一次，不要直接断定是 bug。
- 判断依据：429 的响应体是 `{"ok":false,"msg":"操作过快，请稍候"}`，
  而数据损坏是 **500**，两者完全不同。

## 7. 环境坑（这台机器特有）

### 7.1 `git push` 会被网络重置
- 现象：`fatal: unable to access 'https://github.com/...': Recv failure: Connection was reset`
- 但 **`api.github.com` 是通的**，所以项目原本就用 API 推送（`_gb\push_cloud_api.py` 等）。
- 绕法：用 GitHub Contents API（`PUT /repos/{owner}/{repo}/contents/{path}`，
  带 `sha` 做更新），令牌从 `git credential fill` 取。
- 后果：本地 `main` 会比 `origin/main` 多提交（内容其实已在远端），网络恢复后再 `git push` 对齐。

### 7.2 `raw.githubusercontent.com` 容易挂起
- 验证远端文件优先用 **API**（`/repos/.../commits?path=...` 或 contents 接口），
  别用 `raw.githubusercontent.com`，它在这台机器上经常一直挂着。

### 7.3 起重复服务实例
- 端口 8701 只能有一个实例。
- 踩过的坑：一个诊断脚本 `import` 了服务端模块，模块顶端 `app.run()` 直接起服务，
  又因为旧进程刚好在这一刻退出，**它抢到了 8701**，导致"两个服务"混乱。
- 规矩：**不要 import 服务端模块**；要复用它的函数就把代码复制出来单独跑。
- 每次动服务前后都确认一遍：
  ```
  Get-NetTCPConnection -State Listen -LocalPort 8701
  Get-Process pythonw,python
  ```
  正常情况下应该**只有一个** `pythonw` 在听 8701。

### 7.4 `.bat` 在本工具里会卡住
- `启动留言服务.bat` 结尾的 `timeout /t 4` 在无输入环境下会阻塞并报
  `ERROR: Input redirection is not supported`。
- 想重启服务就直接起进程，别经过 bat：
  ```
  Start-Process pythonw -ArgumentList '"D:\WTZ\prts\_gb\guestbook_server.py"' -WindowStyle Hidden
  ```

### 7.5 PowerShell 处理中文
- 用 `Set-Content -Encoding UTF8` 改含中文的文件会**编坏**（写成乱码）。
- 要写含中文的文件：用 `write` 工具，或
  `[IO.File]::WriteAllText($p, $s, (New-Object System.Text.UTF8Encoding($false)))`。
- 控制台想看中文先设：`[Console]::OutputEncoding=[System.Text.Encoding]::UTF8`。

### 7.6 `scripts\` 里的旧脚本路径已失效
- `scripts\prts_check.py` 和 `scripts\prts_verify.py` 里写死的是老目录
  `D:\WTZ\noida\37ed\prts\...`，直接跑必失败，要先把路径改成 `D:\WTZ\prts`。

## 10. 时间碎片接入踩过的坑（2026-10-04）

### 10.1 插入路由时覆盖了装饰器，留下孤儿函数体

- **现象**：`/frags` 返回 500 或 404，但 `py_compile` 通过、`ast.parse` 通过
- **真因**：插入新路由时只删掉了 `@app.route("/frags")` + `def api_frags():` 两行，函数体残留；还把隔壁 `/frag_get` 的装饰器一起吞掉，`api_frag_get` 缩进成了 `api_frags` 的内部函数。缩进合法所以语法校验全绿——**语法合法 ≠ 路由在**
- **怎么修**：比对两份路由表（枚举 `@app.route` 列表），不要只看 py_compile
- **别再来一次**：整段替换前先 grep 目标函数名的行数；改完路由后逐个点名接口还在不在

### 10.2 GET 请求的 token 读不到

- **现象**：前端 GET 调 `/tfrag` 返回 `count:0 / caught_today:false`，POST 才是真值
- **真因**：服务端 `p = request.get_json() or {}` 不读 query string，`?token=` 等于没传
- **怎么修**：前端一律 POST + JSON body
- **别再来一次**：鉴权接口统一 POST；路由里保留 GET 只是为了探活

### 10.3 前端模块直接复制会 ReferenceError

- **现象**：把 index.html 里的模块原样复制到其它页面，整段挂掉
- **真因**：模块引用的 `call()/esc()/pageFile()` 各页面定义不一，且 `pageFile()` 在 index 里是 IIFE 内部函数
- **怎么修**：公共模块自包含：自己定义 `esc/pageFile/apiBase/call/apiToken`，局部声明遮蔽全局
- **别再来一次**：跨页面复用的代码段必须不依赖宿主页面的全局符号

### 10.4 grep 默认区分大小写

- **现象**：说「_cloud 没有 TFRAG 常量」是对的，但因为漏掉了大小写变体没搜到是侥幸
- **怎么别再来一次**：搜常量名时大小写两种各搜一遍，或 `grep -i`

### 10.5 PowerShell 里 `python -c` 的引号地狱

- **现象**：`python -c "..."` 嵌套引号出现 `SyntaxError: unterminated string literal`
- **怎么别再来一次**：用 here-string（`$code = @'...'@; $code | python -`），或直接写临时 .py 再跑
